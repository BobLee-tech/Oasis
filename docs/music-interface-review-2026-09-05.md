**Oasis 共鸣页：前端与功能设计评估**

评估日期：2026-09-05。基于当前工作区源码、本地 Vite 预览，以及 W3C、MDN、web.dev 和 Nielsen Norman Group 的资料。本次只增加分析文档，没有修改应用实现。

评估中区分三种证据：**已复现**表示在本地预览中观察到；**源码确认**表示可从当前控制流或样式直接判断；**设计建议**表示需要通过后续试用验证的改进方向。预览覆盖深色模式下的 1280×720、390×844 和 375×667 CSS 像素视口；不是手机真机、完整可访问性审计或性能基准测试。

当前最值得投入的方向是：让已有的音乐氛围建立在稳定、可预期的操作之上。黑胶、水纹、情绪色与双语歌词已经形成了清晰的风格；布局边界、播放语义、跨面板控制和曲库检索是更迫切的短板。

**1．先以实际实现校准项目现状**

当前曲库是 **110 首**：Yorushika 68 首、Atarayo 11 首、Miku 31 首。音乐主组件为 868 行，播放器 hook 为 671 行，已经超出 AGENTS.md 中的旧规模描述。

已有能力值得保留：

- 全局单例音频，切换站内场所可继续播放；对象存储音频地址映射与歌词发布流程已经存在。
- 桌面唱机与选碟/歌词双区；移动端唱片、歌词、歌单三段切换。
- 单曲循环、列表顺序续播、洗牌袋随机播放；上一首在进度超过 3 秒时先回到曲首。
- 实时频谱水纹、唱片惯性旋转、情绪色光场、播放及换曲的音量渐变。
- 日文/双语/中文歌词、点击句子定位、手动浏览、回到此刻、纯器乐与加载/缺失状态。
- 共用 ticker、页面不可见时跳过视觉采样、触屏隔帧、canvas 频谱、桌面曲库行 content-visibility。

因此，搜索、队列等新增能力应沿着这套界面扩展；歌词同步、频谱和移动端适配本身已经存在，不应再次作为“从零补齐”的建议。

布局根源见 [OasisResonance.tsx](../src/components/OasisResonance.tsx:420)，移动端分支见[同一组件](../src/components/OasisResonance.tsx:271)。键盘冲突两端分别是[全局监听](../src/components/OasisResonance.tsx:216)和[歌词局部监听](../src/components/resonance/LyricField.tsx:496)。选歌语义见 [useSoundscape.ts](../src/hooks/useSoundscape.ts:563)。

桌面外层可采用 `minmax(0, 7fr) minmax(0, 5fr)` 一类两列结构，但比例仍需按内容验证。关键是只保留一道栏间距，并保证短视口下控制区不被唱机挤出。1024px 是当前桌面切换断点，不能单凭宽度认定设备既有足够高度、又适合重视觉。

**3．视觉设计：让气氛与信息各有位置**

目前右侧依次叠放频谱、大歌名、艺人、摘句、歌词/选碟切换、分类、选碟台标头，最后才轮到曲目。1280×720 的初始预览中，列表主体只露出很少内容。切到歌词后，标题与频谱又改变位置，切换按钮也随布局上移。这增加了重新寻找信息的成本。

建议先明确“选曲”和“聆听”的空间分配：选曲时，固定高度的曲目信息加列表，给列表稳定的剩余空间；看歌词时，扩大歌词阅读区域，保留稳定的标题和控制锚点。黑胶依然可以是视觉焦点，但它的尺寸应服从当前任务和视口。双栏之间切换内容时，标签入口的位置尽量固定，减少文字跨区迁移。

桌面初始样式中，大标题约 32–60px，而分类、语言切换、艺人、播放模式和来源常只有 7–11px。适合作为唱片铭牌的微字，被广泛用于功能信息。建议将主要操作文字试调到 12–14px、曲目名维持约 15–16px；微字仅保留在不影响决策的装饰上。这些尺寸是设计起点，需要结合字体与实际设备验证。

情绪色应该有不同用途的派生色：光晕用原色，文本用可读墨色，按钮使用经过对比度验证的前景与底色组合。项目已有 `oasis-accent-ink`，但选中标签和播放按钮仍直接采用“原始情绪色 + 白色”。按源码的纯色组合计算，白色与初音绿 #39C5BB 约 **2.13:1**，与樱粉 #FFB7C5 约 **1.64:1**。110 首曲目的白字/情绪底色组合均低于 4.5:1；这说明动态色需要系统处理，不是只调整某一首歌。这里的计算不等同于包含所有透明层与动态背景的完整页面审计。普通文字通常应达到 4.5:1，大字为 3:1；关键图形还需单独检查非文本对比度。[W3C：文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

深色模式还有叠加因素：暗角覆盖整个舞台，列表顶部/底部 mask 渐隐，次要文字本身又低透明。歌词同时使用按行距离衰减与容器遮罩，远处文字会很快接近不可读。建议把最强暗角留给装饰区域，缩短内容渐隐区，并提供适合完整阅读的歌词浏览态。

播放模式建议显示“随机 / 列表循环 / 单曲循环”，用图标辅助。当前 sequence 实际会在末尾回到首曲，用“列表循环”更符合行为。`RND / SEQ / LOOP` 可以留在装饰铭牌，主要操作入口使用明确文案。

**4．播放功能：先统一规则，再增加功能**

当前分类只改变 filteredPlaylist；自动续播和上一首/下一首仍遍历全量 PLAYLIST。因此筛选 Miku 后，下一首仍可能进入 Yorushika。单纯浏览分类不一定应该修改队列，但界面必须让两者的关系清楚。

建议建立三个独立概念：

- **曲库**：全部 110 首及其检索结果。
- **当前播放列表**：从哪张专辑、哪个策展歌单或全部曲目开始播放。
- **播放历史**：实际播放过的顺序，供随机模式下的上一首使用。

建议的规则是：切换分类只浏览；点击“播放此专辑”或在有明确范围的列表中启动播放时建立队列；后续切歌沿这个队列进行。界面以“正在播放：某专辑 · 随机”显示来源，列表中提供“定位当前曲目”。不要让用户靠猜测理解筛选是否影响下一首。

随机模式现在正向、反向都进入 `getNextShuffleIndex`，所以曲首按上一首会再抽一首，并非返回刚才的歌。这是缺少历史栈的直接表现。保留洗牌袋，同时增加历史索引，即可兼顾不重复和可回退。[当前续播逻辑](../src/hooks/useSoundscape.ts:434)

播放器还需要比 isPlaying 更完整的状态。当前仅从 play/pause/loadedmetadata 等事件更新状态，播放失败主要 console.warn，缺少加载、缓冲、失败与重试的界面。预览第一次直达音乐页时，浏览器日志出现自动播放被拦截，页面没有解释原因。建议至少表达“待播放、加载中、播放中、已暂停、缓冲中、失败”，提供“点击开始”“重试”“下一首”等对应动作。`play` 事件表示 paused 从 true 变为 false，并不足以证明已经稳定出声；应结合 playing、waiting、error 与 play() 的 Promise 结果。[MDN：play 事件](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play_event)、[MDN：play()](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play)

切歌入口应共用同一套流程，统一处理当前曲目、时间归零、旧时长清除、新时长未知、播放意图、失败回退。现有 advanceTrack、playTrack 和 switchTrack 对这些状态的处理不同，容易在新媒体元信息尚未到达时暂时显示旧进度或时长。

音量渐变的审美价值可以保留，但应缩短操作等待感：暂停要等 650ms 渐出结束才触发 pause；播放中点新歌先等 800ms 才换源，再进行约 1000ms 淡入，且上一首/下一首走另一条更直接的路径。建议用户动作立即获得视觉反馈，音频渐变单独执行；“暂停/切歌意图”不依赖渐变回调才能完成。源码中 changeVolume 会 cancelFade，因而在暂停渐出期间调音量可能取消尚未执行的 pause；这属于需要补回归用例的并发控制风险，尚未在本次 UI 中专门复现。[渐变与暂停](../src/hooks/useSoundscape.ts:550)、[音量变更](../src/hooks/useSoundscape.ts:614)

静音和恢复也宜成为独立状态：当前恢复固定为 0.5，不会回到用户先前设置的音量。先保存偏好音量和静音状态，再处理实际音频增益。音量、播放模式、最后一首可以本地保存；回访时恢复选择并展示继续入口，首次访问的每日一曲仍可保留。恢复播放需要遵循浏览器的用户交互要求。

这些改进对应的专业原则是系统状态可见、行为一致、用户控制和错误恢复；其在 Oasis 中的具体落点是“按下后知道发生了什么，也能方便撤回或继续”。[NN/G：可用性启发式](https://www.nngroup.com/articles/ten-usability-heuristics/)

**5．110 首规模下，找歌应有两条路径**

明确知道想听什么的人，需要搜索；想随便听听的人，需要策展入口。

第一阶段增加曲库内搜索，覆盖曲名、艺人、专辑及常用别名，进行大小写、全半角与空格归一化。现有 ⌘K 只搜文章、场所和动作，可随后加入曲目结果，共用检索逻辑。日文曲目可逐步添加常用中文名或罗马字别名，不必一开始做复杂的全语种搜索。

专辑浏览应允许直接进入、整张播放、收起展开，并保留列表位置。当前从音频 URL 文件夹提取专辑名和年份，界面会受到归档文件名影响；合辑名称中的“2008~2012”还可能被当作发行年份的 2008。建议在曲目数据中显式补 albumId、albumTitle、releaseYear、trackNumber、duration、artwork、aliases。文件路径继续承担播放定位，显示元数据独立管理。[专辑推导](../src/components/OasisResonance.tsx:148)

第二阶段可增加“最近听过”和本地收藏，以及少量站主策展歌单，例如“雨夜”“写作时”“初音旧梦”。每组配一句收录理由，比单纯再增加一个艺人分类更能表达个人花园的气质。单曲详情可以关联站内文章、画作或听歌笔记，让“共鸣”与花园、星图形成内容联系。

**6．歌词：保留表现力，改善阅读控制**

现有歌词系统已包含双语、逐句定位、间奏、手动浏览与跟随状态。下一步重点是增强读者对它的控制。

手动浏览后，代码固定在 4.2 秒无操作时恢复跟随，而且没有要求 isPlaying。阅读一段译文时，用户停下来并不意味着读完了。建议手动浏览期间保持阅读位置，点击“回到此刻”后恢复；或者允许选择自动恢复时机。暂停状态尤其不应自动拉回。[自动恢复逻辑](../src/components/resonance/LyricField.tsx:413)

语言切换已有偏好保存，应继续保留；可以增加两档字号、浏览态的稳定字色，以及放在次级设置中的歌词校准。前端没有可见的失败重试动作，useLyrics 的请求也没有显式超时，建议补齐，避免长期停留在“寻觅词迹”。纯器乐、尚未收录、网络失败应继续保持不同含义。

“待校”与来源目前位于极小的来源行，sm 以下整行隐藏。由于双语译文会影响理解，手机也应能从简洁的信息入口看到来源及待校状态。项目文档说明 `machine` 同时包含机器初译与未经站主审校的导入译文，产品文案宜继续称“待校”，不能一律说成机器翻译。歌词内容质量需要逐首核对；本次没有审查完整曲库的译文或同步准确度。[歌词面板](../src/components/resonance/LyricPanel.tsx:126)、[歌词流程](../docs/lyrics-pipeline.md)

**7．全站陪伴与系统控制**

全局音频能跨页面播放，但站内其他场所没有常驻的播放/暂停入口。建议把紧凑播放条纳入底部系统：提供当前曲目、暂停、下一首、回到共鸣；同时调整现有 bottom-safe-space，避免新增条遮住文章、Dock 或 Miku。手机歌词和歌单复用同一套控制能力。

Media Session 可补上媒体元数据及系统播放、暂停、切歌动作，使支持它的浏览器能与系统媒体界面配合。需要按能力检测渐进增强，并在 Safari/iOS、Android 和桌面浏览器验证实际支持；它不能保证所有设备都具备相同的锁屏、后台续播行为。[MDN：Media Session](https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API)

后续功能可以从场景出发：夜间陪伴适合睡眠定时；与朋友分享适合单曲地址及可选时间点。当前路由没有将 soundscape 纳入 ITEM_VIEWS，因此 `#/resonance/<trackId>` 还不能定位曲目。实现时让音轨 id 和可选时间进入分享链接，并避免把每次自动切歌都写成浏览器历史。[路由](../src/lib/route.ts:22)

**8．可访问性与性能的具体落点**

可访问性不只是给图标补 aria-label。当前桌面唱片是带 role=button 的 div，但没有 tabIndex 和自身键盘行为；移动端唱片只是 clickable div。应使用原生 button，或补全等价行为。全局空格监听要避免覆盖当前焦点按钮的标准激活方式；输入 range 完全透明，焦点也不会显现在可见滑轨上，需要在包裹层显示 focus-visible/focus-within 反馈。[W3C：按钮键盘行为](https://www.w3.org/WAI/ARIA/apg/patterns/button/)

音乐页大量 outline-none 会覆盖 base 层的全局焦点样式，不能因为 index.css 有 focus-visible 就认定各控件已可见聚焦。分类和当前曲目状态也应通过 aria-pressed、aria-current 或合适语义暴露。歌词行用 button 再覆盖成 role=listitem，会削弱动作语义；可将 listitem 放到外层，保留内层按钮语义，并验证辅助技术操作。

手机主要传送键已有 44px 或更大热区，基础不错；语言按钮、桌面静音图标和滑轨仍有提升空间。建议主要操作使用约 44×44px 点击区，图标本身可保持纤细。WCAG 2.2 AA 的最低目标尺寸原则是 24×24 CSS px，另有间距等例外；44px 是本项目建议的舒适目标，不能混称为 AA 一律强制值。[W3C：目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

性能方面，现有共享 ticker、ref 写样式、隐藏页面降载和 canvas 已是合理基础。仍有三处应测量并收敛：

- 唱片旋转与 ReactiveTitle 每帧 text-shadow 没有完整跟随 reduced-motion；CSS 隐藏 ambient 并不会取消它们的 JS 订阅。将 reduced-motion、面板可见性、视图在场状态统一进入动画开关，静止后停止无意义更新。
- 曲目行的无限 height 动画会影响布局，标题 text-shadow 会触发绘制；改为固定高度下的 scaleY 或独立光层透明度。减少布局和绘制动画是浏览器性能指南的明确建议。[web.dev：高性能动画](https://web.dev/articles/animations-guide)
- useSoundscape 对所有订阅者每秒同步 currentTime。Gallery 仅使用 playlist/switchTrack，Miku 只需曲目/播放状态，也会收到时钟更新。拆开命令、低频状态和进度订阅，让列表、画廊和伴侣不用跟着每秒刷新；可采用 React 外部 store 的订阅方式，无需先引入大型状态库。

这些是源码暴露的优化候选，不是本次测出的帧率或耗电结论。应在修改前后用同设备、同曲目、同视图的 trace 比较。对 110 首曲库，优先解决无关组件更新与布局问题，是否需要完整虚拟列表再根据测量决定。

**9．建议的实施次序与验收**

| 阶段 | 实施范围 | 完成标准 |
|---|---|---|
| 第一轮：恢复稳定使用 | 两列网格、短屏布局、手机常驻控制、快捷键隔离、选歌行为、基本加载/失败反馈 | 三个已测视口无重叠与裁切；歌词/歌单内一击暂停；歌词左右键只改变进度；所有播放入口结果一致。 |
| 第二轮：提高日常效率 | 搜索、专辑播放范围、队列与历史、定位在播、静音恢复与偏好记忆 | 能按歌名或别名找到曲目；明确知道下一首来自哪里；随机上一首回到实际历史；恢复静音不突变为 50%。 |
| 第三轮：完善阅读与陪伴 | 歌词浏览态、字号/来源入口、全站播放条、Media Session、策展歌单 | 手动读词不被意外拉回；看文章时能直接暂停；支持的系统控制有效；新增底栏不遮内容。 |
| 后续按使用反馈增加 | 本地收藏/最近播放、睡眠定时、单曲与片段分享、内容关联 | 每项都有明确使用场景，并复用现有曲目和站内内容数据。 |

回归范围应包含：1280×720、1440×900、1024px 临界宽度、390×844、375×667、横屏与 200% 缩放；短/长/多语曲名；亮暗主题及最浅情绪色；键盘和触屏；首次直达、暂停选歌、快速连续切歌、渐出中调音量、缓冲/失败重试；歌词有无译文、纯器乐、请求失败；跨页面播放、回访和 reduced-motion。

测试重点应放在可复现的问题和状态转换：队列/历史/模式的纯逻辑测试，媒体事件与最后一次操作生效的集成测试，以及关键视口的浏览器回归。视觉微调本身不需要堆积与实现逐项同构的单元测试。
