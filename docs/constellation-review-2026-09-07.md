# Oasis 星图：现状评审与下一轮重构方案

日期：2026-09-07。范围：功能设计、信息架构、视觉设计、交互和前端实现方案。本文是设计评审与实施建议，未修改应用代码。

依据：当前源码、既有两轮设计文档、本地运行页面、公开的一手设计案例与规范。本地页面在本次检查中显示 9 篇可见文章、1 个包含 6 篇的合集、3 篇独立文章；这不是对全部后台内容的统计。实际检查了 1280×720 桌面日夜状态、文章星卡、命令搜索和 390×844 手机视口。未做访客研究、完整性能压测或全站无障碍审计。

**一、建议的产品方向**

把星图做成一份有作者气质的知识导览：访客能看懂这里写了什么，选一条适合自己的阅读路线，在文章之间发现有依据的联系，读完后回到原来的位置。

保留“昼为刻本，夜为星野”的视觉资产。重构的中心是信息结构与探索路径。新版可以叫“星野”，副标题使用“按主题漫游 Oasis”；导航仍叫“星图”，内部 orchard 名称不必因此改动。

当前 9 篇的规模尤其需要内容策展。一个 COMP3121 合集就是有价值的主景，不必为了画面热闹虚构多个知识领域。独立文章也应有可读标题和话题提示，保持自己的地位。

三个主要任务：

| 人与情境 | 需要完成的事 | 界面应提供的帮助 |
|---|---|---|
| 第一次来，暂时没有明确目标 | 了解作者兴趣，选一篇开始读 | 主题名、合集简介、推荐起点、少量代表文章 |
| 带着主题来，或刚读完一篇 | 找到对应文章、上下文和下一篇 | 搜索定位、合集目录、直接引用/反向引用、关联理由 |
| 站主整理内容 | 补断链、续写主题、整理阅读次序 | 园丁专用观测手记、可执行的待办 |

**二、值得保留的基础**

- 文章与花园同源，星图不是另一套内容后台；先按可见性过滤，再构图的边界应继续保留。
- 合集自然形成具名星座，选中文章能直接进入阅读舱，星图本身不承担完整阅读器。
- 确定性布局、相机 ref、SVG 和屏幕字号补偿已经存在，适合这个内容规模。
- 昼夜共用视觉语法、少量品牌色、克制的星芒和可关闭图层，都值得继续发展。
- 文章星卡已经支持 `#/constellation/<id>`，节点也已有键盘 Enter/Space 操作；下一轮应补全这条链路。

这些基础意味着无需为了重构引入图数据库、全新路由库或持续运行的物理模拟。

**三、当前最值得处理的断点**

| 优先级 | 证据和现状 | 对用户的影响 | 建议 |
|---|---|---|---|
| P0 | 深色星卡 h2 和容器实测 `color: rgb(0, 0, 0)`，卡面为深蓝黑 | 标题、摘要和阅读入口难以辨认 | 补齐 HTML 前景色与表面色令牌；SVG fill 正确不代表 HTML color 正确 |
| P0 | 小于 768px 显示“请到电脑上展开”，Dock 也会隐藏入口 | 手机访客不能使用按主题探索；文章星图深链也无法展示对应内容 | 先提供主题目录、合集顺序和相关篇目，再考虑触摸总图 |
| P1 | 数据层有 wikilink、shared-tag、nebula、neighbors；视图主要画合集链，星卡只展示合集前后篇 | 同合集之外的知识联系没有成为可使用的信息 | 先在星卡呈现有解释的邻接文章，再实现局部连线 |
| P1 | 首屏标名由“全图最亮”和“分类独苗”决定；亮度由篇幅决定 | 短而适合入门的文章难以成为入口，独立文章可能只有一个点 | 常驻标名优先主题、推荐起点、代表文章；篇幅留在阅读元信息中 |
| P1 | 当前多篇文章采用诗意标题，合集名只有 COMP3121 | 读者难以从图上判断具体内容、难度和阅读收益 | 保留原题，增加一句说明；先复用摘要，必要时添加人工编辑的短注 |
| P1 | 全站已有标题/标签/正文搜索，但命中后统一去 garden | 搜索能够找文章，却不能在星图中建立方位感 | 复用同一索引，在星图情境下提供“在图中定位”动作，并保留“阅读全文” |
| P1 | 星卡无明显关闭按钮和专用 Escape 处理；相机状态只在组件 ref 中 | 退出、返回与继续探索不连贯 | 明确关闭、返回主题和回到全图；跨阅读恢复主题、选中项、相机和焦点 |
| P2 | 时间尺和待照料是访客常驻控制；待照料把种子或超过 30 天未更新都圈出 | 维护信息挤占读者入口，完成的文章也会显得“需要处理” | 维护收进园丁区；时间先放到文章元信息或可选的写作轨迹 |
| P2 | 现有图版框较大，主合集落在左下，大片留白缺少主题解释 | 画面安静，但用户缺乏开始探索的抓手 | 通过主题说明和取景改善构图，不靠增加装饰星填满空间 |

“留白”本身不是缺陷。问题在于留白周围是否有足够清楚的主次、标题和入口。当前值得加强的是阅读方向。

**四、功能结构：总览、主题、文章三层**

总览保留一幅安静的星图，左侧或图版边缘是一小段导览：“这里收录了什么、从哪里开始”。当前只需突出 COMP3121 合集，并给独立文章可理解的入口。后续文章增多，才自然出现更多主题。

点击主题进入主题聚焦：显示主题简介、文章数量、推荐起点，以及可点击的合集目录；相机让该主题进入可读范围，其他内容保留低强调背景。主题名本身必须可操作，不要求用户先猜哪一颗星属于它。

点击文章打开固定位置的星卡。建议顺序为：

1. 原标题与一句具体说明，例如“见招拆招，逢水架桥”下方显示现有摘要“COMP3121 的总结与一些考点”。
2. 阅读时间、所属主题、必要的生长状态。
3. 明确的“阅读全文”。
4. 同合集的前后篇与完整目录入口。
5. 直接引用、被哪些文章引用、共同主题的相关推荐，并写出关联理由。

“共同标签”不能直接叫作“前置知识”。“上一篇”来自创建时间，也不自动等于适合学习的顺序。第一版应忠实展示现有合集顺序；确实需要课程导览时，再由作者指定推荐起点和阅读顺序。

建议的阅读闭环：总览 → 主题 → 星卡 → 阅读舱 → 返回原主题与相机位置。浏览器后退同样要成立。首次从外部链接进入时，没有旧视图可恢复，则围绕该文章提供一个清楚的局部入口。

访客搜索应有可见的文字提示“搜索文章或主题”，键盘快捷键作为补充。主题列表和搜索结果要能直接定位图中节点。无需再做一份独立检索引擎。

**五、关系语义：让每一条线都有依据**

| 关系 | 信息来源 | 展示范围 | 解释方式 |
|---|---|---|---|
| 合集顺序 | 现有 series 与创建时间，未来可选人工排序 | 总览中保留轮廓，主题聚焦时清晰显示 | 同属某合集，第几篇 |
| 文章引用 | 正文中明确解析到的内部链接 | 选中文章的一跳邻域 | 本文引用了它 / 它引用了本文 |
| 共同主题 | 标签成员关系 | 星卡列表优先；用户展开时再画弱线 | 共同讨论某个具体主题 |
| 推荐路径 | 作者明确编辑 | 该主题内部 | 推荐从这里开始，接着读什么 |

总览不展开全部标签边。一跳关系先呈现最相关的少量条目，例如 4–6 篇，其余用“查看全部”保留可达性；这个数是原型起点，需要用真实长标题和屏幕大小调整。

共享“计算机”之类的广义标签不能压过具体引用。可以按标签稀有度与共同标签数量排序，但对外说明仍展示具体理由，不呈现虚假的精确相似度百分比。

图的空间邻近只能表达布局和主题聚集，不能保证语义相似度。尤其现算法让散星靠近第一个匹配标签的合集，并非挑选最相近主题；适合称为启发式布局，不能包装成自动理解知识。

数据层还需要区分“保存所有语义证据”和“画几条线”。当前强关系去重会删除部分共享标签边；若做相关推荐，应该保留同一文章对的多项 evidence，再由视图决定画法。

**六、视觉方向：当代的知识图版**

建议延续现有宣纸与湖夜背景。风格由排版、画面秩序、真实内容和少量材质共同完成。

| 视觉要素 | 建议 |
|---|---|
| 日间 | 暖白纸面、清晰墨色、极轻纹理；减轻外围灰雾与模糊感，让文字像印在纸上 |
| 夜间 | 深蓝黑底、接近白色的主要文字、少量星核光晕；清楚区分内容星与装饰星尘 |
| 初音绿 | 用于选中状态、当前路线和核心操作；浅底文字使用已有更深的青绿色令牌 |
| 樱粉 | 留给少量作者推荐或情绪点缀；语义固定后再使用，不与多种状态混用 |
| 标题 | 沿用站内中文书写气质；主题名负责方向，文章名负责识别；英文合集可用现有衬线字形成节奏 |
| 正文和操作 | 使用清晰的文本层级；主要说明建议 14–16px，次要信息 12–13px；9–10px 不再承担重要动作和知识信息 |
| 连线 | 低饱和、清楚而安静；焦点关系更明晰，次级关系退后，避免所有边发光 |
| 材质 | 纸纹/星尘只承担环境感；字号、边界和信息层级的预算优先于纹理复杂度 |
| 动效 | 主题切换采用短距离相机过渡；选中用稳定光环；减少持续闪烁，尊重 reduced motion |

桌面可以采用“窄导览区 + 主要图面 + 按需星卡”。右侧星卡出现后，相机使用剩余可用区域取景，选中的节点不会躲在面板后面。控制集中在明确的一处：缩放、全图、必要的视图选项。现有全站 Dock 继续使用。

字号和间距应先重新整理成少量统一令牌，再整体替换。当前 CSS 注释说固定五档字号，但实际已包含 9.5、11.5、15、21、27 等额外数值；下一轮需要让文档与实现重新一致。

星核的大小差异可以保留为视觉节奏，但默认入口与常驻标名不再由“篇幅最长”独占。人工指定的推荐起点，使用独立可辨识标记；不要把篇幅、质量、推荐度和引用数混成一项星等。

星名显示采用语义层级：总览主要显示主题与推荐入口；主题聚焦显示完整成员标题；选中时显示邻接关系与说明。标签过密时，优先短注、局部聚焦或目录，不一律降低字号和透明度。

**七、可借鉴的案例与专业依据**

| 案例 | 可借鉴之处 | 在 Oasis 的转译 |
|---|---|---|
| [Figures in the Sky — Nadieh Bremer](https://figuresinthesky.visualcinnamon.com/) | 围绕星座建立具名分组和可探索的信息叙事 | 用真实合集形成能辨认的图案；用主题解释带领用户进入图中 |
| [Wanderings of Stars — Visual Cinnamon](https://www.visualcinnamon.com/art/wanderings-of-stars/) | 作者用同一类星空数据发展出不同时间意象与材质风格 | 借鉴昼夜材质和青色光感的控制；Oasis 的动态只服务聚焦和阅读 |
| [Obsidian Graph view](https://obsidian.md/help/plugins/graph) | 总图、局部图、深度、过滤和键盘操作构成一套探索机制 | 优先做以当前文章为中心的一跳关联；让图有可到达、可返回的局部语境 |
| [Connected Papers 的实际图谱页面](https://www.connectedpapers.com/main/10c0005c16a30ed3e97753ba723bb70d4ba16b70) | 明确说明位置按相似性组织，和引用树的语义不同 | 每种布局与边都说清代表什么，避免把共享标签显示成先修关系 |
| [Burritt 星图集，美国国会图书馆馆藏](https://www.loc.gov/resource/g3180m.gct00292/?sp=1&st=list) | 历史星图可作为具名星座、图版边界和图例体系的素材来源 | 保留刻边、款识与图例的秩序；装饰应给文章标题和操作让位 |

上述案例中的功能描述来自其官方页面。把它们用于 Oasis 的做法属于本次设计建议，并非案例作者的结论。参考作品的视觉语言不意味着直接使用其图片素材。

Shneiderman 的信息可视化研究提出先总览、再缩放和过滤、按需查看详情，同时讨论关系、历史与提取任务。对本站的启发是：已有总览和星卡，下一轮应补主题过滤、关联解释与返回历史，而不是只增加绘制密度。[原论文](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)

无障碍要求必须进入视觉设计：普通文字最低 4.5:1、大号文字最低 3:1；AA 点击目标一般至少 24×24 CSS px，规范另有间距、等效入口等例外。本站手机主要操作建议以约 44×44px 作为更舒适的设计目标。拖拽功能应提供可点击的等效路径，如主题定位、缩放按钮和目录导航。[文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)、[拖拽替代](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)

**八、手机：保留任务，重新组织界面**

旧方案明确决定撤下手机版。这是当时为了避免横版星图缩成细条所作的取舍；现在以功能实用为目标，建议采用新的响应式策略。

手机默认显示可纵向阅读的主题目录：主题标题、短介绍、文章数、推荐开始阅读的条目。点击主题进入合集目录，上方可以保留一小幅有身份感的星座图；点击文章打开底部详情或独立详情页，继续阅读和查看关联。

手机和桌面共享文章、主题与关系数据，布局分别适配设备。手势漫游总图可以后置，核心操作不能依赖 hover、双指缩放或准确点中微小星点。

星图文章深链在手机上直接展示对应星卡/文章导览；不要先把用户送回一个无关列表。任何折叠或视觉降级，都应保留相同的内容可达性。

**九、前端重构边界与代码级问题**

建议按职责渐进拆分，避免为拆文件一次性改完所有交互：

| 模块 | 职责 |
|---|---|
| 内容关系层 | 按可见性生成文章实体、主题成员、引用和证据，独立于坐标 |
| 布局层 | 生成/恢复星位，处理局部碰撞，维护布局版本 |
| 相机与拾取 | 世界坐标和屏幕坐标换算、缩放/平移、面板避让、命中检测 |
| 标签层 | 语义优先级、真实尺寸测量、冲突剔除和稳定性 |
| 桌面图面 | 渲染星体、主题轮廓、焦点边与背景 |
| 导览与星卡 | 主题入口、目录、关联说明、阅读动作；手机复用同一数据 |
| 观测手记 | 管理员任务，独立于访客默认图面 |

保留 React、SVG、现有 hash 路由和 ref 相机。第一阶段无需新增数据库结构；短介绍可先用摘要，关系使用现有正文链接和标签。确认作者确实需要持续维护推荐起点、顺序和短注之后，再扩展元数据，避免建立另一份易过期的文章标题表。

需要具体处理的实现问题：

- **HTML 颜色继承**：`src/index.css:489` 定义了 `--sky-ink`，但 `.oasis-sky` 没有对应的 `color`；SVG 标签另设 fill，因此呈现“图中文字正常、星卡黑字”的分裂。星卡入口位于 `src/components/OasisOrchard.tsx:737`。
- **空合集误判**：`OasisOrchard.tsx:583` 把 `figureOf(post.id) !== litFig` 用于背景淡出。独立文章和未选中态都可能得到 null，等值不表示属于同一合集。应先构造明确的焦点集合，再派生亮暗，覆盖无合集、单篇合集和无选中的场景。
- **命中区单位不一致**：`OasisOrchard.tsx:375` 又把数据层 hitR 扩成至少 `26 / viewRef.k`，并未包含 SVG 外层到屏幕的完整变换。数据层的不相交性质不能直接等价为最终屏幕命中区保证；统一屏幕距离拾取，并用目录提供密集节点的等效入口。
- **标签只在特定时机排版**：`OasisOrchard.tsx:364` 在 fit 后摆标签，resize 只 write，相机缩放改变恒定屏幕字号对应的图面间距。应在容器尺寸、字体就绪、显示层级和面板占位改变时触发布局；拖动中避免每帧重新测量全部文字。
- **星位稳定有前提**：`layoutStars` 依赖创建时间及此前全部输入；已有测试证明按时间追加时旧星稳定。补录早期文章、删除早期内容、更改合集/标签或改变可见数据集合时，需要额外定义稳定策略。可先按 id 缓存本会话已落星位和布局版本，验证需求后再考虑持久化；访客缓存只包含公开内容。
- **视野不等于星位**：即使旧星世界坐标不变，`plateBounds` 变化触发 fit，也会改变它们在屏幕上的位置。用户已经开始探索之后，新增数据不应强制回到全图；提供“有新文章”提示和自愿重置。
- **引用方向损失**：`constellation.ts:595` 起通过无向 pair 去重，双向引用会只保留先遍历到的一项来源。需要分开保存有向引用，再聚合视觉边，以支持引用/反向引用和准确解释。
- **主题邻接不完整**：`constellation.ts:648` 只把 post–post 边加入 neighbors；四篇以上标签走 hub 时，成员不会因此自动成为文章邻居。孤星判断也可能把有主题归属的文章当作“无航线”。主题成员关系和直接引用应分别计算，避免靠渲染边反推全部语义。
- **分类颜色被硬编码**：视图 `TINT` 与图例只覆盖 note/project/thought，而 PostType 支持自定义分类。应该从分类元数据生成一致的符号映射，超出颜色预算时采用中性色并给文字标识。
- **日历口径要统一**：时间尺混用公历年、UTC 的立春年位置和本地日期。若保留这个图层，应统一“自然年/月”或“节气年”的口径，并说明节气近似，而非把均分刻度包装成精确历法。
- **文档与遗留逻辑**：旧环形布局工具、时间环注释、不可见的标签 hub 等仍与现界面混在一起。先检查调用，再清理确实无使用者的工具和误导性注释；有测试并不等于仍属于当前产品需求。

当前星尘数随世界包围盒面积增长；每颗内容星又由多层 SVG 图元组成。性能应测布局、标签测量、React 提交和实际帧耗时，不能只用节点数推断。先限制装饰预算、减少重复计算；只有实测出现瓶颈时，再考虑 Worker 计算或 Canvas 装饰层。现有 600 篇测试测的是数据层耗时，不证明 600 篇的标签和浏览器交互同样流畅。

**十、落地顺序与验收**

| 阶段 | 工作包 | 可检查的结果 |
|---|---|---|
| P0 基础可用 | 深色星卡颜色、关闭/返回、清晰字号、手机主题目录与深链详情 | 日夜能读，手机能找到并打开同一篇文章 |
| P1 阅读闭环 | 主题导览、推荐起点、搜索定位、引用/反向引用列表、相机恢复 | 首次访客能从主题找到文章，读完继续探索 |
| P2 视觉与交互 | 主题聚焦、一跳连线、标签层级、面板避让、装饰预算、昼夜材质精修 | 真实长标题可读，聚焦有方向，图面保持安静 |
| 后续按需 | 人工阅读顺序、跨主题路径、布局持久化、写作轨迹和性能升级 | 由实际内容规模及使用反馈驱动 |

先把当前 9 篇做成好用、完整的一页，再用 30/100/300 篇的模拟语料暴露密度问题。模拟数据必须标清，与真实内容隔离。

验收不只看截图：

- 请 3–5 位不熟悉本站的人尝试理解主题、找到指定文章、说出两篇文章为何关联。首次定位到可读文章可先以 30 秒内作为试验目标，不当作现有成绩。
- 检查 390px、768px、1280px 的日夜布局；标签、卡片与 Dock 不遮挡关键动作。
- 键盘可从主题目录进入星卡、读文并返回；关闭时焦点回到原入口。hover 与 focus 获得等效信息。
- 搜索、主题切换和返回不产生意外的全图重排；跨阅读保留已选主题和相机。
- 引用不存在、没有关联、数据加载中、离线缓存、零篇文章都有明确状态；没有关系时诚实显示，不制造连接。
- 用浏览器工具测量真实拖动和缩放性能；若以 60Hz 为目标，帧预算约为 16.7ms，需要在代表性设备上验证，而不是写成保证。
- 应用改动阶段运行 build、lint、关系/路由测试，以及少量覆盖完整阅读闭环的交互检查。本次仅交付方案，未运行这些实现验收。

这轮最值得投入的内容是：清晰可读的星卡、能看懂的主题导览、可解释的局部关系、完整的手机路径。它们也会为后续的视觉精修提供更有力量的主景。
